# Maize AI — Analytics Feature PRD (v1)

**Date:** March 29, 2026
**Author:** Simon Kleffner
**Status:** Draft — for implementation by development team

---

## 1. Overview

Add a professor-facing analytics dashboard to Maize that surfaces anonymized, aggregated insights about how students are using their AI teaching assistant. The goal is to transform Maize from a student support tool into a teaching insight tool — helping professors understand where students are struggling, when they're engaging, and which course materials drive the most questions.

---

## 2. Business Context

### Why now
- Multiple professor conversations have surfaced the question: "What can I see about how students are using it?"
- Analytics is a key differentiator from generic AI chat tools (ChatGPT, etc.) that offer zero instructor visibility.
- Analytics creates a natural upgrade incentive from lower pricing tiers to mid-tier and above.

### Pricing tier gating
- Analytics is **not available** on the Small tier (1-49 students).
- Analytics is **available** starting at the Medium tier (50-125 students) and above.
- Rationale: Below ~50 students, professors can typically maintain direct awareness of student struggles. Above 50, they lose that visibility. Analytics fills the gap, and gating it creates a real upgrade incentive.
- A professor who manages multiple TAs across different courses should only see the analytics tab for TAs where they have a Medium tier or higher subscription. TAs on the Small tier should show a tasteful upgrade prompt where the analytics tab would otherwise appear.

---

## 3. User Experience

### Where it lives
- Analytics appears as a new **tab** within the existing professor portal, alongside whatever existing tabs/views are present (e.g., TA management, file uploads, settings).
- The tab is labeled **"Analytics"** or **"Insights"**.
- When a professor clicks the Analytics tab, they see a list of their TAs that have analytics access (Medium tier+). Clicking into a specific TA shows the dashboard for that course.
- For TAs on the Small tier: the Analytics tab shows a brief message explaining that analytics is available on the Medium plan and above, with a link to upgrade.

### Anonymization (non-negotiable)
- **No individual student data is ever displayed.** Professors must never be able to identify which student asked which question.
- All data is presented in aggregate: counts, percentages, distributions, topic clusters.
- Individual queries are never shown verbatim to professors. Only clustered topic summaries are displayed.
- The UI should include a visible note (e.g., a small text line or info icon) stating: "All data is anonymized. Individual students cannot be identified."

## 4. V1 Feature Requirements

### 4.1 Usage Over Time (Quantitative)

**What it shows:** A time-series chart of total student interactions with the TA over the life of the course.

**Requirements:**
- X-axis: dates (daily granularity by default)
- Y-axis: number of student queries/interactions
- The professor can select a date range (e.g., last 7 days, last 30 days, all time)
- Overlay markers or annotations for known assignment due dates if the professor has entered them (optional in v1 — this can be a manual input field where professors add key dates, or it can be deferred to v2 - DEFER TO V2)
- Show peak usage times in a secondary view or tooltip: e.g., "Most active hours: 9-11 PM"

**Why this matters:** Professors can see engagement patterns, identify spikes before exams or due dates, and understand when students are studying.

### 4.2 Top Topics (Qualitative)

**What it shows:** A ranked list or bar chart of the most common topics students are asking about, derived from clustering raw queries.

**Requirements:**
- Display 5-10 topic clusters ranked by frequency (e.g., "Net Present Value calculations — 34%", "WACC and cost of capital — 21%", "Reading financial statements — 15%")
- Each topic shows: cluster label, percentage of total queries, absolute count
- Topics are generated by sending batched student queries to an LLM with a prompt that categorizes them into thematic clusters based on the course content
- This clustering can run on-demand when the professor opens the analytics view, or nightly as a background job — whichever is simpler to implement in v1
- The professor can select a date range to filter which queries are included in the clustering
- Topic labels should be descriptive and course-relevant (not generic labels like "Topic A")

**Why this matters:** This is the single highest-value data point. A professor who sees "47 questions about bond pricing and only 3 about equity valuation" knows exactly what to spend more time on in the next lecture.

### 4.3 Summary Stats

**What it shows:** A set of key metrics displayed as simple cards or numbers at the top of the dashboard.

**Requirements:**
- **Total interactions:** lifetime count of student queries for this TA
- **Interactions this week:** count for the current 7-day period
- **Peak day:** the single date with the highest query volume
- **Peak hour:** the most common hour of day for queries (e.g., "10-11 PM")
- **Unique sessions:** approximate count of distinct usage sessions (a session can be defined as a group of queries from the same user within a 30-minute window, or whatever proxy is technically simplest — this does not need to be precise, just directionally useful)

**Why this matters:** Gives professors a quick snapshot without needing to dig into charts.

## 5. Data Requirements

### What data already exists
- Every student query is already logged with: timestamp, TA ID, message content, and (presumably) some session or user identifier.
- The analytics feature is primarily a **read layer** on top of existing data. No new data collection is required.

### What data processing is new
- **Topic clustering:** Batching student queries and sending them to an LLM to categorize into topic clusters. This is the only new "intelligence" layer.
- **Aggregation queries:** Counting interactions by date, by hour, by TA. Standard database aggregation.

### Privacy and data handling
- The analytics pipeline must never expose individual query text to the professor.
- Topic clustering should operate on batches of queries and return only cluster labels and counts.
- If the LLM prompt for clustering includes raw student queries, those queries must not be stored or cached in any professor-visible location — only the resulting cluster labels and counts are persisted/displayed.

---

## 6. Out of Scope for V1

The following are intentionally deferred to v2 or later:

- **Email digest:** Weekly summary email sent to professors (requires transactional email integration)
- **Document coverage view:** Showing which uploaded materials are referenced most/least
- **Session-level trends:** Week-over-week progression of topic distribution ("Week 1: basic concepts → Week 5: application problems")
- **Assignment due date integration:** Automatic import of due dates from an LMS (manual entry is acceptable for v1)
- **Export/download:** Ability to export analytics data as CSV or PDF
- **Comparative analytics:** Comparing engagement across sections or semesters
- **Real-time dashboard:** Live updating; periodic refresh is acceptable for v1

---

## 7. Success Criteria

- A professor on a Medium+ tier plan can open the Analytics tab, select a TA, and see all three components (usage over time, top topics, summary stats) populated with real data.
- A professor on a Small tier plan sees a clear upgrade prompt instead of analytics.
- No individual student can be identified from any data displayed.
- Topic clustering produces meaningful, course-relevant labels (not generic categories).
- The analytics view loads within a reasonable time (a few seconds is fine for v1; it does not need to be instant).

---

## 8. Open Questions

- **Clustering frequency:** Should topic clustering run on-demand (when professor opens the tab) or as a scheduled background job? On-demand is simpler but slower; background is faster to display but requires a job scheduler. Implementation team to decide based on architecture.
- **Session definition:** What constitutes a "unique session" given the current data model? Implementation team to determine the simplest reasonable proxy.
- **Date range for topic clustering:** Should there be a limit on how many queries are sent to the LLM for clustering at once (e.g., max 500 per batch)? Implementation team to determine based on cost and performance.
- **Tier enforcement:** How is the tier/plan associated with a specific TA in the current data model? Implementation team to confirm the linkage exists or flag if it needs to be created.
